S-Move Dealer — Developer Onboarding / Local Setup

Clone, configure, run, build, deploy.

Compiled 2026-07-30 from the SMD App codebase and its .claude/launch.json.

1. Prerequisites

  • Node.js 20.19.0 (pinned in .node-version) — use nvm or equivalent to match it exactly.
  • Git access to SMoveTech/smove-dealer on GitHub.
  • The project's .env file (not committed — get it from whoever last worked on the app; see the Environment & Config Reference doc for what every variable does).

2. Clone & install

git clone https://github.com/SMoveTech/smove-dealer.git
cd smove-dealer
npm install

Place the project's .env in the repo root. server.js calls require('dotenv').config() as its first line, so it loads automatically — no extra step needed.

3. Run it locally

node server.js

Not npm start — that runs dist/server.js, the obfuscated production build, which won't exist until you've run npm run build and is painful to debug. For day-to-day development, run the plain source directly. The app listens on port 3001 by default (PORT env var).

A launch config already exists at .claude/launch.json for tools that read it (name dealer-app, runs node server.js on port 3001).

4. The build step — when you actually need it

npm run build runs obfuscate.js, which produces the obfuscated dist/ tree that Railway actually deploys. You only need to run this locally if you're specifically debugging a production-only issue (e.g. testing whether a new file is correctly picked up by SRC_FILES) — it is not part of the normal edit/test loop.

5. Local-dev gotchas

  • The #1 trap: a new top-level .js file works perfectly when you run node server.js locally, then crashes Railway with MODULE_NOT_FOUND after deploy — because it's missing from SRC_FILES in obfuscate.js. Add it in the same commit. See the Deployment Runbook §2.
  • Sessions are in-memory by default — unless DATABASE_URL is set in your local .env, restarting the dev server logs everyone out. Fine for most local work.
  • No sandbox/mock mode for external services — Stripe, Twilio, Gmail and Anthropic all need real credentials to exercise those code paths locally. Prefer test-mode keys/numbers over production credentials where the provider supports it (e.g. Stripe test mode) rather than testing payment flows against the live account.
  • Database schema drift — some tables that the app depends on were created directly in the Supabase dashboard and have no migration file in this repo (see the Data Model doc). Don't assume the repo's migrations//supabase/migrations/ folders are a complete picture of the live schema.
  • The obfuscated build isn't meant to be readable — never debug from dist/; always work from the source files.

6. Deploying your change

See the Deployment & Release Runbook — in short: push to main, Railway builds and deploys automatically, there's no staging environment.
