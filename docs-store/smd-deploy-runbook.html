S-Move Dealer — Deployment & Release Runbook

How a change goes from a local edit to live on shop.s-move.co.uk.

Compiled 2026-07-30 from the SMD App codebase and Railway/GitHub config.

1. The pipeline

There is no staging environment and no CI pipeline — a push to main on GitHub (SMoveTech/smove-dealer) is picked up directly by Railway, which runs:

  1. npm install && npm run build — installs dependencies, then npm run build runs obfuscate.js, which obfuscates the SRC_FILES list into dist/ (see the Technical Architecture doc §1.1 for the full mechanism).
  2. npm start — runs node dist/server.js, i.e. the obfuscated build, never the repo-root source.

Railway's restart policy is ON_FAILURE with a maximum of 3 retries (railway.json) — if the app crashes on boot 3 times in a row it stops retrying and stays down until a new deploy or a manual restart.

2. Before you push — the one rule that matters

Any new top-level .js file that gets require()'d must be added to SRC_FILES in obfuscate.js, in the same commit. Miss this and the file simply isn't in dist/ — the app runs fine locally (against un-obfuscated source) but crashes on boot in production with MODULE_NOT_FOUND. This is the single most common way a deploy breaks. Always check obfuscate.js's SRC_FILES array before pushing a commit that adds a new route file or top-level module.

Static assets (public/, views/) and one-off scripts (backup.js, seed-canvass.js, backfill-*.js) are deliberately excluded from the build — they're never meant to run through Railway.

3. Database changes

There is no Supabase CLI wired into this project (no supabase/config.toml, no supabase db push in any script). New tables and columns are applied manually by pasting the migration SQL into the Supabase SQL editor for project wayqlbhdflyioacqbwtb. Still write and commit a numbered file under supabase/migrations/ (or the top-level migrations/ folder, both exist and are both used) even though nothing auto-applies it — the Data Model doc already flags several live tables that were created ad-hoc in the dashboard and never captured in a migration file at all, which makes reconstructing the schema from the repo harder than it should be. Don't add to that debt.

Sequence for a schema-dependent code change: run the SQL in Supabase first, confirm it applied (Supabase table editor), then push the code that depends on it — the two are never atomic, so a code deploy that assumes a column exists before you've added it will error at runtime.

4. Verifying a deploy

  • Watch the Railway deploy logs for the build to go green and for the boot log line (no MODULE_NOT_FOUND, no uncaught startup exception).
  • Hit a public, unauthenticated page first (e.g. the shopper homepage or /directory) to confirm the process is actually serving traffic.
  • If the change touched a webhook (Stripe checkout or billing), send a test event from the Stripe dashboard's webhook testing tool and confirm it returns 200 rather than a signature-verification failure.
  • If the change touched email, run a real sign-up/verification flow end-to-end rather than trusting logs alone — Gmail API failures can be silent (fire-and-forget with .catch() in several places).

5. Rolling back

Two options, in order of preference:

  1. Railway dashboard rollback — redeploy the previous successful build from Railway's deployment history. Fastest option, no code changes needed.
  2. git revert the offending commit(s) and push to main — use this when the previous Railway build is no longer available or when the fix needs to be more surgical than "go back to the last build."

There's no feature-flag system for a gradual rollout — every push to main goes to 100% of traffic immediately.

6. Known deploy gotchas

SymptomCause
Boot crash, MODULE_NOT_FOUNDNew .js file missing from SRC_FILES in obfuscate.js — see §2
New feature works locally, 500s in productionAn env var the feature needs was added locally to .env but never added to Railway's Variables tab
Stripe webhook suddenly failing signature verificationThe webhook endpoint was recreated in the Stripe dashboard (new secret) without updating STRIPE_WEBHOOK_SECRET / STRIPE_BILLING_WEBHOOK_SECRET on Railway — there are two separate webhooks and two separate secrets, easy to update the wrong one
New table/column errors ("column does not exist")Code deployed before the corresponding SQL was run in the Supabase editor — see §3
