How the platform collects, uses, stores and protects personal data, and how to handle data-subject requests. This is an internal reference for the controller — distinct from the public-facing Privacy Policy published on the app itself.

⚠ Interim safe basis. The public Privacy Policy is itself marked interim (v1.0, 29 Jul 2026) — prepared internally, not yet solicitor-reviewed. This doc takes the same cautious position: the longest applicable retention period is assumed, and standard safeguards are treated as required. Items still needing formal sign-off are listed in §9.

3. Data subjects' rights & how to handle them

  • Access (SAR): export the person's records across the tables in §2 (seller by seller_id; shopper by customer_id/token; canvasser by canvasser_id). Respond within one month.
  • Rectification: sellers self-serve most of their own data via "My Shop"; shoppers via account settings; anything else corrected via the admin console.
  • Erasure: honour except where a legal retention obligation applies (financial records tied to sponsorship/donations — see §4). Canvass prospect data that never converts to a seller already auto-purges after 30 days (§4) — a genuine automated erasure control, not just policy.
  • Portability: provide data in a structured format (JSON/CSV export).
  • Objection / restriction: the mailing list and marketing emails already carry one-click unsubscribe, honoured automatically; stop any other non-essential processing on request.
  • Log every request (who, when, what was done) for accountability.

6. Security measures

  • Service-role DB access server-side only; no browser-side Supabase client ships an anon key. Row-Level Security is enabled on every table (77/77, confirmed by dashboard audit) as defence-in-depth.
  • Admin access behind a device-approval gate plus session login; WebAuthn/passkeys supported for admin and staff.
  • Seller access via bearer token verified server-side; shopper access via OTP-issued bearer token (no password to leak); canvasser access via bcrypt-hashed PIN.
  • Server-to-server calls from SMO's shared bot are gated by an API key compared with crypto.timingSafeEqual — not a plain string match.
  • Secrets in environment variables only; never committed. See Environment & Config Reference.
  • Hourly backups to a separate location (excluding OAuth token tables); code in version control. See Backup & Disaster Recovery.
  • Passwords/PINs stored hashed, never in plain text.

7. Personal data breach response

  1. Contain — revoke affected credentials/devices/keys.
  2. Assess — what data, whose, how many, likely harm.
  3. Report to the ICO within 72 hours if it's a reportable risk to individuals, via the ICO's online breach-reporting service. Alex (alex@s-move.co.uk) is the responsible person.
  4. Notify affected individuals if high risk.
  5. Record the breach and remediation regardless of whether it's reportable.

8. DPIA

A full Data Protection Impact Assessment is not mandatory at SMT's current small scale for SMD (no large-scale or systematic special-category processing). The canvassing subsystem captures business premises and shopfronts, not individuals' homes, which keeps that risk lower than SMO's customer/address data. Given AI processing of enquiry/chat text and photos, a short screening assessment is nonetheless advisable — see §9.
