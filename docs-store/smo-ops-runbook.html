S-Move Operations — Operations & Incident Runbook

How to deploy, roll back, and recover the platform — and every known failure mode with its fix. If something looks broken, start with §4: most "outages" are a known, benign cause.

Draft 2026-07-28 from operational history. Keep current whenever a new failure mode or fix is learned.

2. Deploy / release

  1. Commit to the repo and push to GitHub — Railway deploys from GitHub only; a local commit that isn't pushed does nothing.
  2. Edit source files; the build regenerates dist/ on deploy. Don't edit dist/ directly.
  3. Watch the Railway deploy go green. If the app still looks wrong after green, it's almost always the PWA/service-worker cache, not the deploy (see §4).
  4. Verify a key path (load the admin console, send a test action) before considering it done.

3. Rollback

  • Fast path: git revert <bad commit> then push — Railway redeploys the reverted state.
  • Deeper: the pre-refactor-backup tag on GitHub marks the state before the server.js split — restore from there if a structural change went wrong.
  • Never restore/overwrite data files (smove_data.json) or customer data to "fix" a code bug — fix the code. Data restore is a separate, deliberate action (§6).

4. Known failure modes & fixes

Work through these before assuming a real outage.

SymptomLikely causeFix
App "looks broken" right after a deploy that went greenStale PWA / service-worker cache on the device — NOT the deployHard refresh; clear the app's cache / bump the service-worker version. The deploy is fine.
Bank sync / financial import stopped; Monzo calls failingMonzo Strong Customer Authentication expired (~every 90 days)Re-authorise Monzo via the OAuth flow in the Financials area; tokens refresh into the monzo_tokens table.
Outbound calls fail — "Premature close" / ENETUNREACH (Anthropic, email)Railway's IPv6 egress is brokenForce IPv4 on all outbound (undici family:4). Ensure the Anthropic key is stored unquoted.
Sudden "Invalid API key" 401s from Supabase while prod seems otherwise fineFree-tier IP throttle from bursting queries — the 401 is misleadingWait it out. Do NOT rotate the key or touch .env — the key is fine.
"Can't log in" — rejected before the password is checked (403)Admin device gate, not a bad passwordApprove the device: /admin/device-setup?key=<ADMIN_DEVICE_SETUP_KEY>.
Emails not sendingRailway blocks outbound SMTPEmail must go via the Gmail API over HTTPS (GOOGLE_CLIENT_ID/SECRET + gmail_tokens). EMAIL_USER/PASS is legacy fallback only.

5. Monitoring & alerts

  • adminAlert() texts the owner numbers on key events (new customer, quote accepted, call-me, messages, requests, inventory) within an 8am–9pm window. Recipients: ADMIN_ALERT_NUMBERS.
  • Watchdog / critical alerts escalate to OWNER_ALERT_NUMBER; backup alerts use ALERT_SMS_NUMBER.
  • If alerts go silent, check Twilio balance/credentials and the 8am–9pm gate before assuming nothing happened.

6. Backup & restore

  • Data: hourly Supabase export to D:\S-Move Backups via the "S-Move Hourly Backup" scheduled task (silent/S4U). Backups are sacred — never disable without a replacement.
  • Code: GitHub is the backup — every deploy is a commit.
  • Restore: use restore-from-recovery.js / backup.js against a chosen backup. Restore is deliberate and approved — never as a reflex to a code bug. Confirm the target before overwriting anything.
  • Financial data is never hard-deleted (soft-delete + tombstones + purge policy). Respect the entity boundary (5 Jun) and VAT boundary (1 Jul).

7. Periodic / scheduled work

  • Hourly: Supabase backup.
  • ~Every 90 days: Monzo SCA re-authorisation (§4).
  • Monthly: consolidated storage invoices auto-generate (storage_invoice_records).
  • Ongoing: VAT columns/reconciliation live from 1 Jul 2026 (standard 20%).
