1. Executive Summary

S-Move Operations is the core software platform powering S-Move Removals Ltd (SMR), a professional removals and storage company. The platform manages the complete lifecycle of customer jobs — from AI-powered initial enquiry through quoting, booking, shift rostering, payroll, storage management, and financial reporting. It serves four distinct user groups: customers, field staff, administrators, and accountants, via dedicated portal interfaces.

4. Database Architecture

4.1 Overview

The database consists of 35 tables in Supabase PostgreSQL. The primary access control is architectural: all database access is server-side using the Supabase service-role key, which is never shipped to any browser — clients never connect to the database directly, so no client can reach another customer's data. Row-Level Security is enabled at the database level on tables where applicable as an additional guard (see the RLS audit for current per-table status). JSONB columns are used for flexible structured data.

6. Core Workflows

6.1 Customer Enquiry to Booking (Full Lifecycle)

Phase 1 — Enquiry

  1. Customer visits app.s-move.co.uk/customer in their browser
  2. Customer completes registration form (name, email, phone) → POST /api/register
  3. System creates customers record with quote_status: pending
  4. Confirmation email sent automatically via the Gmail API (HTTPS)
  5. AI chat assistant activates (Claude claude-haiku-4-5-20251001)

Phase 2 — Information Gathering (Multi-Channel)

Information gathering for quoting purposes can take place across multiple channels. All data collected feeds the same customer record and is consolidated into an admin-facing quote summary.

Channel 1 — In-Portal Chat Messaging:

  1. Claude guides the customer through a structured conversation in the portal chat
  2. Job type, property details (type, floors, lift access), from/to addresses and move date collected
  3. Claude offers two inventory approaches: photo upload or room-by-room verbal description
  4. (Photo path) Customer uploads up to 5 photos per room → stored in Supabase Storage
  5. (Photo path) Claude Vision analyses each photo and generates a room-by-room item inventory
  6. (Verbal path) Customer describes contents room by room; Claude extracts structured inventory
  7. Claude calculates an estimated cubic footage (CuFt) total from the inventory gathered
  8. Claude performs parking analysis using Google Street View images of both addresses
  9. Structured data markers extracted automatically: <<<INTAKE_UPDATE>>>, <<<DATA_CORRECTION>>>, <<<PARKING_NOTES>>>
  10. customers record updated in real time with all job details as they are confirmed

Channel 2 — SMS Conversation (see Section 6.3 for full detail):

  1. Customer texts the S-Move Twilio number; AI chatbot collects all intake data over SMS
  2. Once email address is collected, customer is sent a portal invite link to continue via portal

Channel 3 — AI Phone Call (see Section 6.2 for full detail):

  1. Customer calls +44 7414 140899; Claude handles a full spoken intake conversation
  2. All collected data written back to the customer record on call completion

Channel 4 — Email:

  1. Gmail is synced via OAuth and all inbound/outbound emails are logged against the customer record in comm_logs
  2. Admin can view the full email thread history alongside all other communication channels in one place

Channel 5 — In-Person Survey Visit:

  1. For larger or complex jobs, an in-person survey visit can be offered to the customer
  2. Admin records survey findings and inventory notes directly against the customer record
  3. Survey data is combined with any portal/phone/SMS data already gathered

Quote Presentation to Admin:

  1. All gathered information is consolidated in the admin console: inventory summary, estimated CuFt, parking notes, property details, photos, and communication history
  2. Admin has a single unified view of everything needed to generate an accurate quote

Phase 3 — Quoting

  1. Admin reviews the consolidated job information in the admin console
  2. Admin generates quote PDF via quote-generator.js (pdfkit) — includes job breakdown, inventory summary, CuFt estimate, and pricing
  3. Admin sends the quote from the "Send to customer" panel: the PDF is regenerated and previewed, then sent on confirmation — the paired SMS fires too and the Gmail API confirms it landed in Sent. Customer-facing email is button-only (nothing is auto-emailed on a status change); each send records a sent_documents row with the sent date
  4. The quote PDF is stored permanently on the server and in Supabase Storage — accessible at any time via GET /api/customer/:token/quote.pdf regardless of how much time has passed
  5. Customer views quote in the portal; revised quote versions are also stored permanently with version suffix (quote-v2.pdf etc.)

Phase 4 — Booking Confirmation

  1. Customer accepts quote via portal chat → POST /api/customer/:token/quote-response
  2. booking_status set to confirmed; confirmed_date recorded
  3. Booking is confirmed automatically, but no invoice is auto-sent — admin sends the deposit invoice (or the full balance invoice if the move is within 5 days) from the "Send to customer" panel
  4. If the job date is fewer than 5 days away, the deposit step is skipped and the full balance invoice is prepared instead
  5. Customer pays via the Stripe link; webhook fires to POST /api/stripe/webhook
  6. payment_status updated; job is now confirmed and ready for rota

6.2 AI Phone Intake Workflow (Twilio Voice)

The AI phone line acts as both a standalone intake channel and as a co-pilot for customers already using the portal. Because the AI has full read access to the customer's live record, it can answer questions, read back status, and guide the customer through any stage of their job journey over a live phone call.

Call Flow

  1. Customer calls S-Move AI phone number: +44 7414 140899
  2. Twilio routes inbound call to POST /api/voice/inbound
  3. Server returns TwiML response directing Twilio to open a ConversationRelay WebSocket
  4. Twilio opens persistent WebSocket connection to WS /api/voice/relay
  5. Claude Haiku model handles the conversation turn-by-turn via speech-to-text / text-to-speech

6.3 SMS Intake Workflow

  1. Customer sends a text message to the S-Move Twilio number
  2. Twilio POSTs the message to POST /twilio/incoming
  3. System looks up the customer by phone number in the customers table
  4. If not found: a new SMS enquiry customer record is created
  5. AI chatbot (buildSystemPrompt with sms_intake: true) responds via Twilio SMS
  6. Conversation loop continues: customer replies → AI extracts intake data turn by turn
  7. AI collects: name, email, job type, from/to addresses, move date, property details
  8. When email address is collected: a portal invite link is sent to the customer via SMS
  9. Customer clicks the link and transitions to the full web portal experience
  10. All data collected over SMS is already populated in their portal on first login

6.6 Shift Rostering Workflow

Shifts are organised by team. Multiple teams can operate on the same day, each with their own roster of jobs. A team can be assigned multiple jobs in a day, worked through in sequence.

  1. Admin confirms rota: PATCH /api/admin/customer/:id/rota-confirm → rota_confirmed: true
  2. Admin creates teams for the day (e.g. Team A, Team B) and assigns jobs to each team
  3. Admin posts shifts: POST /api/admin/customer/:id/shifts/post — creates shift rows (one per role slot) with status: open
  4. Each shift is assigned to a crew_group (team name), allowing multiple jobs to be grouped under the same team for the day
  5. Shift start time is set per job; where multiple start location options exist (e.g. depot or direct to job), the available options are presented to staff
  6. Flexible tasks (in-house jobs or tasks not connected to a customer booking, such as cleaning, assembly, or deliveries) can also be assigned to a team on the same day via POST /api/admin/flexible-tasks/:id/assign
  7. Staff browse open shifts via their portal: GET /api/staff/:token/open-shifts
  8. Staff apply for a shift: POST /api/staff/:token/shifts/:shiftId/apply → creates shift_applications row
  9. Admin reviews pending applications: GET /api/admin/shift-applications
  10. Admin accepts an application: PATCH /api/admin/shifts/:id/assign → shifts.assigned_staff_id set; status changes to assigned
  11. Admin publishes the day: POST /api/admin/shifts/publish-day → SSE broadcast to all connected staff
  12. Staff are notified of their shift details, team assignment, and meeting point options
  13. Staff select where to meet their team: POST /api/staff/:token/shifts/:shiftId/meeting-choice (a location choice, not remote vs in-person)
  14. Move day: staff mark job complete via portal: POST /api/staff/:token/customer/:customerId/complete
  15. Staff submit their finish time: POST /api/staff/:token/shifts/:shiftId/finish-time — or admin manually enters the finish time: POST /api/admin/shifts/:shiftId/finish-time/manual
  16. Admin approves or rejects the submitted finish time; approved time is used for payroll calculation
  17. shifts.status set to completed

6.7 On-Day Workflow — Loading & Unloading Signoff

On move day the customer portal is used to capture digital consent at both the loading and unloading stages. This provides a clear record of completion and customer agreement at each point.

Loading Signoff

  1. Once loading is complete at the collection address, the crew lead confirms completion in the staff portal
  2. The customer is prompted in their portal to review and digitally sign that all items have been loaded
  3. Customer signs via POST /api/customer/:token/signoff (type: vacated) — confirms all items removed from property
  4. Timestamp and signoff recorded against the customer record; admin notified via SSE

Unloading Signoff

  1. Once unloading is complete at the delivery address, the crew lead confirms completion in the staff portal
  2. The customer is prompted to digitally sign that all items have been delivered and nothing is missing
  3. Customer signs via POST /api/customer/:token/signoff (type: delivery) — confirms all items received
  4. Timestamp and signoff recorded; admin notified via SSE

Job Completion

  1. Staff mark the job as fully complete: POST /api/staff/:token/customer/:customerId/complete
  2. Admin is notified automatically via SSE that the job has been marked complete by the crew
  3. Job status updated to completed; customer portal reflects job complete state

6.8 Post-Job Workflow

  1. Job completion event triggers the post-job sequence automatically
  2. Admin console flags the job as complete; any outstanding final balance is chased if not yet paid
  3. 2 days after job completion: automated review request contact sent to the customer (email / SMS)
  4. Customer invited to leave a Google review or provide feedback
  5. Any damage claims submitted by the customer via the portal (POST /api/customer/:token/damage-claim) are reviewed by admin and responded to
  6. Job record remains permanently accessible in the admin console and customer portal for reference

6.9 Payroll Workflow

  1. All shifts for the pay period must have admin-approved finish times
  2. Admin opens payroll panel in admin console
  3. Admin triggers payroll batch: POST /api/admin/payroll/payments
  4. System iterates all staff with completed shifts in the pay period
  5. Total hours computed per staff member using staff_start_time → approved finish time
  6. Gross pay calculated: hours × hourly_rate from staff_members table
  7. Mileage reimbursement added from staff mileage log (£0.45/mile)
  8. Payslip PDF generated per staff member via pdfkit
  9. Payslip stored in payslips table as JSONB data
  10. Admin reviews all payslips: POST /api/admin/payslips/approve-and-send
  11. Payslip PDFs emailed to each staff member
  12. Staff download payslips via portal: GET /api/staff/:token/payslips

6.10 Storage Management Workflow

  1. Customer requests storage via portal, or admin creates container record directly
  2. Admin creates container: POST /api/admin/storage
  3. Record includes: date_in, container_number, location, pricing (per_week / per_month)
  4. Staff deliver goods to storage facility; update inventory: PATCH /api/admin/storage/:id/inventory
  5. Admin confirms container details: PATCH /api/admin/storage/:id/admin-confirm
  6. Customer confirms they agree with details: POST /api/customer/:token/storage/confirm
  7. On the 1st of each month: storage invoices are automatically generated for all active containers and emailed to customers — no admin action required
  8. Direct debit is encouraged as the preferred payment method; customers are prompted to set up a Stripe direct debit to cover recurring monthly storage charges automatically
  9. Customer pays via portal (Stripe card, direct debit, or manual): POST /api/customer/:token/storage-payment-complete
  10. When customer is ready for return: POST /api/customer/:token/storage/return
  11. Admin schedules redelivery: POST /api/admin/storage/book-redelivery
  12. Shift created for redelivery; container date_out_actual recorded; container status closed

7.2 Dynamic System Prompt Architecture

The AI system prompt is built dynamically per customer by buildSystemPrompt() in server.js. It is regenerated on every request so the AI always has the latest data. The prompt includes:

  • Customer name, job type, from/to addresses, confirmed move date
  • Quote amount, quote status, quote revision number
  • Booking status, payment status, deposit amount paid
  • Inventory summary and estimated CuFt (if gathered)
  • Parking analysis notes for both addresses (if analysed)
  • Full rota and shift information (if confirmed)
  • Previous conversation context (message history)
  • Special mode flags: sms_intake, parking_analysis, photo_mode
  • Structured output markers: <<<INTAKE_UPDATE>>>, <<<DATA_CORRECTION>>>, <<<PARKING_NOTES>>>

When the server detects these markers in the AI response, it extracts the structured JSON payload and updates the database automatically — without requiring admin intervention.

19. Known Constraints & Operational Notes

  1. Railway ephemeral filesystem: All files written to local disk (/uploads/, /quotes/, /invoices/, etc.) are wiped on each Railway deployment. Supabase Storage is the persistent master for all customer-facing documents.
  2. Supabase Storage buckets required: Both photos and documents buckets must exist in Supabase before the first deployment.
  3. Gmail OAuth: Gmail tokens require manual re-authorisation if the app is migrated to a new Railway project (OAuth redirect URI changes).
  4. Monzo OAuth: Monzo tokens must be re-authorised after any Railway project migration.
  5. Process management: Railway manages process restarts natively via Docker restart policies. PM2 is not used in the Railway deployment.
  6. CSP disabled: Helmet Content-Security-Policy middleware is disabled to allow inline scripts in the portal HTML files.
  7. Monolithic server.js: The main server file is 7,150 lines / 414 KB. Newer features are correctly separated into route modules; older features remain in server.js.
  8. Session secret: If session drops occur after Railway deployment, add a SESSION_SECRET environment variable in the Railway dashboard.
  9. Single process: The app runs as a single Node.js process. Horizontal scaling would require session state to be moved fully to Supabase (admin_sessions already persists there; SSE client Maps do not).
