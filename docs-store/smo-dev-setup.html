S-Move Operations — Developer Onboarding & Local Setup

Get the platform running locally, make a change, and ship it. Assumes access to the GitHub repo and the SMO Supabase project.

Draft 2026-07-28 from package.json and the working setup.

1. Stack

  • Runtime: Node.js (recent LTS). Package name smove-server, entry server.js.
  • Framework: Express + express-ws (WebSockets), helmet, express-rate-limit.
  • Data: Supabase (@supabase/supabase-js), service-role server-side.
  • Key libraries: @anthropic-ai/sdk (Claude), stripe, twilio, googleapis (Gmail/Places), web-push, @simplewebauthn/server (passkeys), pdfkit / pdf-lib (documents), exceljs (payroll export), sharp (images), dotenv, javascript-obfuscator + html-minifier-terser (build).

2. Prerequisites

  • Node.js + npm, and git.
  • Access to the GitHub repo (deploy source of truth) and the SMO Supabase project.
  • The environment variables — see the Environment & Config Reference. At minimum you need SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, APP_DOMAIN, and the keys for whatever feature you're working on.

3. First run

  1. git clone the repo and cd into it.
  2. npm install
  3. Create a .env in the project root with the variables from the Environment reference. dotenv loads it automatically. Never commit .env (it's gitignored).
  4. npm start (runs node server.js). The server listens on PORT (set it in .env).

Port note: on the main dev machine port 3000 is reserved by the OS — use another port locally (the Claude Code preview uses an auto-port around 3939 with an --env-file). Watch for zombie node processes holding a port after a crash.

4. Build & the dist/ folder

  • npm run build (runs build.js) minifies/obfuscates front-end assets into dist/.
  • The server serves dist/ assets when present. For local development, if you want to see raw source changes without building, move dist/ aside — otherwise you'll be looking at the last built output.
  • Always edit source, never dist/; the build regenerates it on deploy.

5. Tests

  • npm test runs the smoke test (node --test tests/smoke.test.js). Run before pushing.
  • See the Test Plan for the broader QA approach.

6. Database & migrations

  • Schema lives in Supabase. Four committed migrations are in migrations/ (device approvals, accounting tables, photo rooms, receipts); the rest of the 35 tables are maintained directly in Supabase.
  • Helper scripts exist for DB work: migrate.js, backup.js, restore-from-recovery.js, excel-sync.js. Read a script before running it — some touch live data.
  • Never point local dev at anything that writes over live customer/financial data. Respect the data-safety rules.

7. Deploy

  1. Commit, then push to GitHub — Railway auto-deploys from GitHub only.
  2. Watch the deploy go green (see the Operations & Incident Runbook).
  3. If the app looks stale afterwards, it's the PWA service-worker cache, not the deploy.

8. Gotchas

  • Outbound must be IPv4 — Railway's IPv6 egress is broken (undici family:4); affects Anthropic + email. Keep the Anthropic key unquoted.
  • Email goes via the Gmail API over HTTPS (Railway blocks SMTP).
  • Supabase free-tier throttle can return a misleading "Invalid API key" 401 when you burst queries — wait it out, don't rotate keys.
  • Login 403 before password = device gate; approve via /admin/device-setup?key=….
