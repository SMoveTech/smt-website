2. Database backup — how it actually works

backup.js doesn't rely on a fixed table list — it dynamically discovers every table exposed by the Supabase REST schema at run time, so a newly-created table (even one created ad-hoc in the dashboard, per the schema-drift notes in the Data Model doc) gets backed up automatically without any code change. Each table is fetched in pages of 1000 rows, the JSON is gzipped, and the file is written read-only (chmod 0o444) so it can't be accidentally overwritten. Retention is the newest 336 files (~14 days of hourly backups) — older files are pruned automatically.

Deliberately excluded (the DENYLIST in backup.js):

  • monzo_tokens — OAuth secrets; if lost, reconnect Monzo rather than restore stale tokens.
  • session — transient Express session store; churns constantly, no recovery value.

3. Storage backup — a gap to flag

storage-backup.js mirrors three buckets: item-images, item-drafts, seller-logos (incremental — skips files already present locally, since catalogue images are treated as immutable). It does not cover the canvass-photos bucket, which holds shopfront/recon photos captured by the field canvassing app. If that bucket were lost, those photos would not be recoverable from the current backup set — worth adding to storage-backup.js's bucket list.

4. Restoring — the honest current state

There is currently no dedicated restore script for SMD (SMO has a restore-from-recovery.js; SMD does not). Restoring today would be a manual, deliberate process:

  1. Locate the relevant dated .json.gz backup file(s) in D:\S-Move Backups.
  2. Decompress and inspect the table dump to confirm it's the right point in time.
  3. Re-insert/upsert the rows back into Supabase via the service-role client (e.g. a short one-off script using the same @supabase/supabase-js client as the rest of the app) — there is no ready-made tool for this today.

As with every S-Move product: never restore or overwrite live data as a reflex fix to a code bug — fix the code. Restoring data is a separate, deliberate, approved action, because it can silently undo real customer/seller activity that happened after the backup was taken (new orders, new listings, payments).

Recommended next step: build a restore script mirroring SMO's restore-from-recovery.js, so a restore is a tested, repeatable command rather than an improvised one under pressure.

5. Storage buckets not covered by the daily backup — Supabase's own redundancy

Supabase Storage itself is durable (object storage with its own redundancy) — the daily mirror is a defence against accidental deletion or a Supabase-side incident, not the only copy. The gap in §3 is specifically about the canvass-photos bucket having no independent copy outside Supabase.
