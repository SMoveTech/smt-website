1. Schema drift — read this first

SMD's schema has drifted from source control in both directions, which matters for anyone trying to reconstruct the database from the repo alone:

  • Tables with no CREATE TABLE anywhere in the repo (hand-created directly in the Supabase SQL editor, actively used today): sellers, customer_accounts, staff_accounts, admin_webauthn, staff_webauthn, approved_devices, seller_tokens, customer_tokens, seller_recommendations, seller_enquiries, canvass_products.
  • Migrations exist but the table is never referenced in application code (likely dead — from an earlier, more ambitious schema draft): tenants, collection_slots, collection_bookings, bundle_opportunities, staff_performance, trend_events, seasonal_patterns, acquisitions, margin_performance, external_data_sources, trend_signals, regional_demand, push_subscriptions, market_trends (counted in an admin stat but never written to).

Treat this table as the source of truth for what's live, and treat any full-schema export from Supabase as more authoritative than the migration files.

2. Row-Level Security

RLS is enabled on every table — confirmed, not partial. Verified 2026-07-21 directly against the Supabase dashboard's pg_tables.rowsecurity (the actual source of truth for the live database): 77/77 SMD tables RLS-on, none off. This includes every table in this dictionary, regardless of whether a migration file for it exists in this repo.

The migration files and schema.sql understate this: many actively-used tables (sellers, customer_accounts, canvass_products, etc. — see §1) were created directly in the Supabase SQL editor, so their RLS was switched on there too, never captured in a committed .sql file. Reading the repo's SQL alone would wrongly suggest RLS is missing on most tables — it isn't. Treat a live dashboard/query check as authoritative over anything in this repo when the two disagree.

Posture is defence-in-depth on two independent layers: (1) the server always connects with the Supabase service/secret key, which bypasses RLS entirely — there is no browser-side Supabase client in the app, so the anon/public key is never shipped to a client; (2) RLS is on for every table regardless, so even a leaked anon key would still be blocked at the database level. Sensitive tables (tokens, OAuth stores, enquiries, donations) are RLS-on with no policy, locking them to the service role only; a handful of public-marketplace tables (e.g. items, enquiries) carry a policy that intentionally allows public read/insert.
