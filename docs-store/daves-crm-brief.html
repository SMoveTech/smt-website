Council & Stakeholder Contact Tracker — Task Brief

For: Dave Sisson  ·  From: Alex

Purpose: Dave's first real Claude Code build — a genuinely useful internal tool for S-Move Dealer (SMD), not a throwaway exercise. A hands-on way to learn to work with Claude.

The people to load into the tool come from the SMD project's Go-to-market panel on this dashboard; the brief points Dave there rather than pasting contacts in.

Why this exists

For SMD we need to approach a lot of key people — economic development officers, BID/town-centre managers, portfolio councillors, business-gateway contacts — across several councils. Right now there's no shared, single place that tells us both:

  • Who we're trying to reach and why they matter
  • How to reach them (their contact details)
  • What's happened so far — when we contacted them, how, and what came back
  • What's next — whose turn it is and when to follow up

Without that, we duplicate effort, miss follow-ups, and can't catch each other up quickly. This app is the single source of truth for outreach so either of us can open it and instantly see where everything stands.

The two halves of this task

There are deliberately two things to do here. The second is as important as the first.

Half 1 — Build the app

A small web app that lets us:

  1. Keep a list of people to contact — name, organisation, role, which council/area, why they matter, and a priority.
  2. Store their contact details — email, phone, address, website/LinkedIn, and which is the best route in.
  3. Log every contact attempt — one entry per interaction: date, method (email / phone / in-person / letter), who did it, a short summary, and the outcome.
  4. Log emails properly — where contact was by email, keep a record of what was sent and what came back (subject, date, direction sent/received, and the message), so either of us can read the thread without digging through inboxes.
  5. Track status & next steps — each person moves through a simple pipeline (Not contacted → Contacted → Responded → Meeting → Won / Dead), with a "next action" and a due date so nothing goes cold.
  6. Stay coordinated — both point at the same shared database, so whatever one logs, the other sees.

Keep it an MVP first. Get the above working end-to-end before adding anything clever.

Half 2 — Get the people into it (the real learning bit)

The contacts are deliberately not pasted into the brief. Pulling them together is part of the exercise.

  • The source is this Build system — open the S-Move Dealer project and read the Go-to-market panel: the councils, what we ask them for, how we frame it, the named officers / BIDs / councillors, and the local champions. Use the co-pilot to find your way around and understand who matters and why.
  • Then verify before loading anyone in. Council and BID roles change, so use Claude's web search to confirm each person is still in post and their detail is current — the panel itself says to confirm roles before addressing anyone by name.
  • Rules:
    • Only use publicly available sources (council / BID / business-gateway pages).
    • Never invent a name or an email. If no individual is listed, use the official team inbox and note that no individual was found.
    • Where a role can't be confirmed, flag it in the app as "confirm before contacting" rather than guessing.
    • Record where each detail came from (source URL).
  • Load the verified people in as the starting dataset.

Ground rules for the build (house style)

  • Stack: Node.js + Express backend (a single server.js to start). Plain HTML + CSS + vanilla JS on the front end, served by the Node server. No React / Next / build tooling unless checked first. Keep it boring and standard.
  • Database: Supabase (Postgres) on Dave's own free Supabase account. Claude walks him through signup + creating a project. It's a throwaway project — not connected to any live S-Move / customer database. Alex ports the tables into the live project on handover.
  • Name every table with an outreach_ prefix (outreach_contacts, outreach_interactions, outreach_emails, outreach_next_steps) so they stay tidy and collision-free alongside our other tables.
  • Read all Supabase details from env vars (SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY) — never hard-coded — so the app can be re-pointed at the live project on handover with no code change.
  • Security model: the browser never talks to Supabase directly and never sees a key. The browser calls the Node server; the server uses the service-role key (in .env, git-ignored). RLS on for every table.
  • Every table gets id (uuid), created_at, updated_at, and a nullable deleted_at. Soft-delete only — never hard-delete.
  • Never commit secrets. Keys live in .env; provide a .env.example with placeholders.
  • No git remotes or Railway deployment — build and run locally; Alex handles go-live.
  • A ready-made conventions file, council-crm-CLAUDE.md, captures all of this — copied into the project as CLAUDE.md so Claude follows it automatically.

How the database works

Claude writes the SQL, but it can't click around the Supabase website — creating the project and running the SQL are browser steps. The flow:

  1. Claude walks Dave through creating his own free Supabase project and copying its URL + service-role key into .env.
  2. Claude writes the whole data model into one commented schema.sql (tables + RLS); Dave pastes it into Supabase → SQL Editor → Run.
  3. Build and test against his own project until it works.
  4. On handover, Alex runs the same schema.sql in the live project and re-points the app via env vars — no code change. The trick: agree table names + variable names up front, and it slots straight in.

The README carries a short "Database setup" section with the click-by-click so anyone can repeat it in two minutes.

How to work with Claude

★ Biggest tip — show Claude your screen. Press Win + Shift + S to grab a screenshot of whatever you're asking about, then paste it into Claude's chat bar with Ctrl + V. Claude can see the image, which saves a huge amount of explaining — and it works both ways: Claude can look at what's on your screen and guide you through it, step by step. Setting up Supabase is the perfect example — keep snapping your screen and Claude walks you through every stage.
  • Open a terminal in the project folder and run claude; point it at this brief and CLAUDE.md.
  • Ask for a plan before any code, review it, then let it build.
  • Build in small steps and test each one: contact list → interaction log → email log → status/next-steps.
  • When something breaks, paste the actual error back to Claude rather than hand-fixing.
  • Never paste real secrets (service-role keys, passwords) into the chat — keep them in .env.
  • Ask Claude to explain anything you don't understand — that's the point of the exercise.
