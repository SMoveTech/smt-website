S-Move Dealer — Technical Architecture

Full system architecture: stack, app structure, core workflows, AI usage, security and data safety.

Compiled 2026-07-30 from a full read of the SMD App codebase (E:\S-Move\SMD App). Regenerate/review after any significant change to routes, schema or the build process.

1. Stack & deployment

Node.js 20 (pinned 20.19.0) + Express 4, deployed on Railway via Nixpacks. Key libraries: @supabase/supabase-js (DB + Storage), @anthropic-ai/sdk, stripe, twilio, googleapis (Gmail), sharp (images), multer (uploads), express-session + connect-pg-simple, bcryptjs, @simplewebauthn/server (passkeys), web-push, express-rate-limit.

1.1 Build & obfuscation — the SRC_FILES gotcha

npm run build runs obfuscate.js, which reads a hard-coded SRC_FILES array (currently server.js, database.js, sidebar.js, dunning.js, data-milestones.js, gmail-mailer.js, campaign.js, sms.js, claude.js, geography.js, rate-limit.js, plus every file under routes/), obfuscates each one (control-flow flattening, dead-code injection, string-array encoding, self-defending), and writes the result into dist/, mirroring the source layout. Railway's start command runs only dist/server.js — never the repo-root source.

The trap: any new top-level .js file that gets require()'d must be added to SRC_FILES in the same commit, or it's silently missing from dist/ and the app crashes on boot in production with MODULE_NOT_FOUND — even though it runs perfectly locally against the un-obfuscated source. Static assets (public/, views/) and one-off scripts (backup.js, seed-canvass.js, backfill-*.js) are deliberately excluded — they run directly via Task Scheduler or node locally, never through the Railway build.

2. App structure — five PWAs

public/ holds five manifests, one per audience, each scoped to its own path with its own theme colour and icons: manifest.json (shopper, scope /), seller-manifest.json (/seller), admin-manifest.json (/admin), staff-manifest.json (/staff), canvass-manifest.json (/canvass) — plus two separate service workers (sw.js, canvass-sw.js).

views/ holds one HTML shell per surface: index.html (shopper home), directory.html, item.html, storefront.html (shop page, reused for canvass shop-preview), checkout success/cancelled pages, seller.html / seller-apply.html, admin.html, staff.html, canvass.html, plus coming-soon.html (beta splash), 403.html, design-system.html, and static legal/marketing pages (terms, privacy, for-shops, support, accountant, contact).

3. server.js — how it's wired

  • IPv6 workaround — forces dns.setDefaultResultOrder('ipv4first') and net.setDefaultAutoSelectFamily(false) at boot, because Railway's IPv6 egress silently black-holes outbound HTTPS to the Anthropic API (and formerly SMTP). No dedicated undici agent — the fix is at the Node DNS/socket layer.
  • Trust proxy — app.set('trust proxy', 1) so secure session cookies work behind Railway's TLS-terminating proxy.
  • Stripe webhooks mounted with express.raw() before express.json(): /api/billing/webhook (sponsorship subscriptions — activates/cancels sponsor slots, books ledger income/fees, triggers dunning on failure, records donations) — this is the only Stripe flow actually live today. A second /api/checkout/webhook (item-purchase completion) exists in code but is not the live buying path — see §4.10.
  • Sessions — express-session backed by connect-pg-simple when DATABASE_URL is set, else in-memory. SESSION_SECRET is required in production.
  • Admin device gate — a custom smdd HttpOnly cookie, checked by a requireApprovedDevice middleware, applied to /design-system, /admin and /admin/*. Devices are approved via a keyed setup URL or an in-PWA one-time 6-digit pairing code texted to admins.
  • Beta gate — sidebar_config.beta_mode checked against a smea early-access cookie, applied to /shop/:slug, /directory, /contact, /item/:code, and the catch-all route.
  • Scheduled jobs (all setInterval/setTimeout at boot): engagement-score recalculation (30 min), data-collection milestone emails (daily), sidebar-score recalculation (30 min), dunning sweep (6h), financial soft-delete purge (daily, 14-day grace), canvass prospect-product purge (daily, 30-day retention), advertising campaign schedulers (off by default), stale-reservation expiry (every 60s).
  • Error handling — per-route try/catch returning JSON {error}; webhook handlers verify Stripe signatures and 400 on failure; most non-critical side effects (SMS alerts, ledger writes) are fire-and-forget with .catch() so they can't fail the primary request.

4. Core workflows

4.1 Seller onboarding / "My Shop"

Public application (POST /seller/apply) requires accepted terms and verified email+phone, checks a blocklist, creates the seller record, and — fire-and-forget — extracts brand colours from the logo/website via Claude and, if the applicant came from canvassing, ports the canvasser's recon profile and captured product photos onto the new live shop. "My Shop" settings (colours, listing order, "holiday mode", delivery info, VAT display) are all edited through a single update endpoint that enforces a strict column allow-list. Note: "holiday mode" is implemented as shop_paused / shop_paused_message — pausing the shop with a custom message — not a dedicated boolean field.

4.2 Directory browsing / discovery ranking

The public browse endpoint fetches active+sold items, applies keyword search and category filter, then a soft location sort: items matching the requested/home town rank first, matching region second, everything else last, stable within each tier. When a category filter is active, results are padded with similar items from progressively broader categories up to a scaling quota. Separately, the sidebar ranking (the "earned, un-buyable" sponsor ordering) is computed by a scheduled job: each seller's score comes from 30-day page views plus this-month vote weight, with an additive, linearly-decaying "new sponsor" boost so a fresh sponsor glides down to its earned score over a configurable number of days.

4.3 Sponsored sidebar / Stripe

A seller-initiated Stripe Checkout subscription at an admin-configurable price (confirmed ~£49/mo is a config value, not hard-coded). Activation, renewal and cancellation are handled entirely by the billing webhook (checkout completed / invoice paid / invoice payment failed / subscription deleted), which also books Stripe income and fees into the internal ledger. Admins can grant a subscription-free "comp" slot with optional auto-expiry, and every approved beta seller gets a free month on go-live (the "Pioneer" flag). Unpaid subscriptions are dropped by the dunning sweep after a configurable grace window.

4.4 Image upload / thumbnails

Uploads are re-encoded to WebP (max edge 1600px, quality 80) for storage, and a 480px-wide WebP thumbnail at quality 72 is generated alongside, stored as thumb/<base>.webp in the item-images bucket. A one-off/re-runnable backfill script uses identical settings for existing images.

4.5 Email (Gmail API)

Railway blocks outbound SMTP ports 25/465/587, so nodemailer is used only as a local MIME builder; the finished raw message is sent via the Gmail API over HTTPS. OAuth tokens are stored in SMD's own gmail_tokens table, independent of SMO's Gmail connection (they share only the Google Cloud OAuth client). Scopes are send + readonly (the latter for campaign bounce-scanning).

4.6 SMS alerts

Operational alerts route through SMO's Twilio number, because SMD's own Twilio account has no phone number of its own — documented explicitly in code. Phone-OTP verification uses a separate Twilio Verify service on SMD's own account. An in-memory 10-minute dedup window prevents double-fires.

4.7 Analytics

A single beacon endpoint inserts {path, session_id} into page_visits, restricted to an allow-listed set of path keys (home, seller_apply, donate, for_shops); the admin traffic dashboard reads it back.

4.8 Canvassing integration

Fully wired into the same app under /canvass, with its own PIN login (bcrypt-hashed). A one-off local script imports an Excel workbook of prospects and seeds canvasser accounts. Signed-up canvass targets get their recon profile and captured product photos migrated into a live SMD seller record on application.

4.9 Donations

Handled in the same billing webhook (a Checkout session tagged with donation metadata): recorded in a donations table and booked as out-of-scope VAT income (a genuine gift, no benefit given — distinct from sponsorship's standard-rated VAT treatment). Recurring donation renewals are caught by the generic invoice-paid handler.

4.10 Buying an item — enquiry today, checkout code not live

No money moves through SMD for an item purchase. The live path is: a shopper opens the enquiry modal on an item (collection / delivery / general), which is sent through the AI chat assistant and can raise a seller_enquiries record reaching the seller's own portal; the item page also displays the shop's preferred contact details (phone, email — whatever the seller has configured), so the shopper can go straight to the seller instead. Payment for the item itself is then arranged and taken directly between shopper and seller, entirely outside SMD.

routes/checkout.js, the /api/checkout/webhook handler, and the orders / order_items / reservations tables (see the Data Model doc) are real code that implements a Stripe-based item-checkout flow — but they are not the current live buying experience. They're groundwork toward a planned phone-as-POS & stock-sync add-on that would let a seller take payment through SMD itself, keeping physical and online stock in sync. That add-on needs further funding to finish building before it can go live — don't describe it as an active feature in user-facing material.

5. AI usage (claude.js)

The Anthropic SDK powers: analyseItemImage (listing photo → title/description/category/price suggestion, informed by staff notes and real sales data), chatWithAssistant (the customer-facing shopping copilot, a tool-use loop that can suggest items, add to wishlist, raise an enquiry, or request a delivery quote), generateListingTips (AI tips for listings with 7+ days of no views), extractBrandColors (from logo/website during onboarding), moderateSellerListing and moderateTestimonial (content moderation), checkBusinessPresence (admin tool: web-search-verifies a seller applicant's business is real before approval), reconBusiness (canvasser pre-visit briefing from a shopfront photo + web search), and extractVisitFromTranscript (turns a canvasser's dictated visit notes into structured outcome data — the raw transcript is never persisted). Several functions use Claude's server-side web-search tool with a continuation loop for longer research tasks.

6. Security

  • Admin — session-based, password checked against either an env-var master account or a bcrypt-hashed admin_users table; WebAuthn/passkey registration also available. All /admin pages and /design-system require the device-approval cookie gate in addition to the session login.
  • Seller — bearer-token auth, verified server-side against seller_tokens.
  • Shopper — no password: email (and optional phone) OTP verification followed by a persistent bearer token.
  • Canvasser — PIN login, bcrypt-hashed.
  • Server-to-server (SMO bridge) — a shared API-key header, compared with crypto.timingSafeEqual, gates the enquiry/verification/apply endpoints used by SMO's shared SMS/voice bot.
  • RLS — enabled on every table (77/77, confirmed 2026-07-21 directly against the Supabase dashboard) — including tables whose RLS was switched on directly in the dashboard rather than via a committed migration. See the Data Model doc for the per-table breakdown. Combined with the app always connecting via the Supabase service key (never a browser-side client), this is defence-in-depth on two independent layers, not a single point of failure.
  • Rate limiting — five named tiers (auth, apply, submit, checkout, read) applied per-route.
  • Bot protection — a honeypot field on the public contact form silently drops bot submissions. No CAPTCHA/reCAPTCHA anywhere in the codebase.
  • Other controls: crypto.timingSafeEqual for API-key comparisons, filter-string sanitisation before PostgREST interpolation, strict cookie flags (httpOnly, sameSite, secure in production), and an allow-listed internal redirect map for the email-click tracker (no open redirect).

7. Data safety

  • backup.js — runs hourly via Task Scheduler; dynamically discovers every table exposed by the Supabase REST schema (so new tables are never missed), fetches all rows in pages of 1000, gzips the dump, writes it read-only to D:\S-Move Backups, and prunes to the newest 336 files (~14 days of hourly backups). Explicitly excludes monzo_tokens (OAuth secrets) and session (transient).
  • storage-backup.js — daily incremental mirror of the item-images, item-drafts and seller-logos buckets to D:\S-Move Backups\dealer-storage; skips files already present locally since catalogue images are immutable.
  • install-backup-tasks.ps1 — registers three Windows Scheduled Tasks: Dealer Hourly Backup, Dealer Storage Backup (daily 02:15), and S-Move Files Mirror (daily 02:45, project files rather than DB/storage data).
