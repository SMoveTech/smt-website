S-Move Operations — Data Protection & Privacy (UK GDPR)

How the platform collects, uses, stores and protects personal data, and how to handle data-subject requests. This is an internal reference for the controller.

⚠ Interim safe basis — adopted 2026-07-29. Where official confirmation isn't yet possible (it's deferred until grant funding lands), this doc takes the most cautious position: the longest applicable retention period is assumed, and standard safeguards are treated as required. It reflects intended safe practice, not yet officially-signed-off policy. Items still needing formal sign-off post-funding are listed in §9.

1. Controller & scope

  • Data controller: S-Move Removals Ltd (SMR), SC892140.
  • ICO registration: SMR processes personal data electronically as a business, so the ICO data-protection fee is assumed to apply. Registration to be completed/confirmed around go-live (pending — see §9).
  • Scope: the S-Move Operations platform (app.s-move.co.uk) and its Supabase database — customer, staff, financial and communications data.
  • Contact for data matters: alex@s-move.co.uk. No statutory Data Protection Officer is required (SMR is a small controller not doing large-scale or special-category processing); the named contact fulfils the role.

3. Data subjects' rights & how to handle them

  • Access (SAR): export the person's records across the tables in §2 (customer records keyed by customer_id/token; staff by staff_id). Respond within one month.
  • Rectification: correct via the admin console; changes are audited.
  • Erasure: honour except where a legal retention obligation applies (financial/payroll — see §4). Use soft-delete/tombstones; document what was retained and why.
  • Portability: provide data in a structured format (JSON/CSV export).
  • Objection / restriction: stop non-essential processing (e.g. marketing) on request.
  • Log every request (who, when, what was done) for accountability.

6. Security measures

  • Service-role DB access server-side only; anon keys never shipped. Row-Level Security is enabled on every table (confirmed by dashboard audit) as defence-in-depth.
  • Admin/accountant access behind password + device-approval gate (2FA-style); passkeys supported.
  • Secrets in environment variables only; never committed. See Environment & Config Reference.
  • Backups hourly to a separate location; code in version control. See Operations & Incident Runbook.
  • Passwords stored hashed; bank details access restricted to payroll functions.

7. Personal data breach response

  1. Contain — revoke affected credentials/devices/keys.
  2. Assess — what data, whose, how many, likely harm.
  3. Report to the ICO within 72 hours if it's a reportable risk to individuals, via the ICO's online breach-reporting service. Alex (alex@s-move.co.uk) is the responsible person.
  4. Notify affected individuals if high risk.
  5. Record the breach and remediation regardless of whether it's reportable.

8. DPIA

A full Data Protection Impact Assessment is not mandatory at SMR's current small scale (no large-scale or systematic special-category processing). Given payroll, financial/banking data and AI processing of enquiries, a short screening assessment is nonetheless advisable and is treated as a pending action (§9).
